# Snowber — neighbors clearing neighborhood snow

A full-stack web app for storm-morning snow clearing. **Homeowners** book a time window and get before/after photo proof, **cleaners** post the hours they can work and are paid per job, and an **operations controller** opens service windows, dispatches cleaners with suggested walking routes, and runs a tool library.

ECE1724 course project · Next.js full-stack (App Router) · TypeScript · Tailwind CSS · shadcn/ui · PostgreSQL + Prisma · DigitalOcean Spaces.

---

## Quick start

**Prerequisites:** Node.js 22 LTS (≥ 20.19) and Docker. Without Docker, use any PostgreSQL 14+ that has the `btree_gist` extension (all standard builds do).

```bash
cp .env.example .env            # then set BETTER_AUTH_SECRET (openssl rand -base64 32)
docker compose up -d            # PostgreSQL on localhost:5432
npm install                     # also runs `prisma generate`
npm run db:deploy               # apply the migrations
npm run db:seed                 # storm-morning demo data
npm run dev                     # http://localhost:3000
```

### A two-minute tour

1. **Controller → Dispatch**: pick tomorrow's *Early birds* window, press **Suggest assignments**, then **Apply**. Drag a waiting job onto a cleaner, or use its *Assign to…* menu. Reorder stops with the arrows.
2. **Ava → My route**: open the first stop and take the *before* photo (starts the job), then the *after* photo (completes it).
3. **Grace** (or the homeowner who owns that stop) sees the status change live, compares before/after with the slider, confirms, and leaves a review.
4. **Ava → Earnings** shows the credit (80% of the price plus 100% of tips, minus rental fees). *Pay out* is simulated.

### How the pieces fit

- **Rendering.** Next.js 16 with *Cache Components*. Every page prerenders a static shell (header, navigation, skeletons); the parts that read the session or the database stream in behind `<Suspense>`. Pages call `requireRole()` inside that boundary, and every DAL function re-checks the role it needs, so a page guard is never the only protection.
- **Mutations.** Forms and buttons call Server Actions (`src/app/actions`). Each action re-reads the session, validates input with the shared Zod schemas, calls the DAL, and calls `refresh()` so the page re-renders in the same round trip.
- **Job lifecycle.** `REQUESTED → ASSIGNED → IN_PROGRESS → COMPLETED → CONFIRMED`, plus `CANCELLED` and `DISPUTED`. The allowed edges and who may take them are a pure function (`src/lib/contracts/job-states.ts`); `transitionJob` / `applyTransition` (`src/lib/dal/jobs.ts`) is the only code that changes a status. It writes the status, timestamps, ledger and payment rows in one transaction with a compare-and-set update (two concurrent requests can't both win), then publishes an event.
- **Matching.** `suggestAssignments` (`src/lib/matching.ts`) takes jobs oldest-first and gives each to the nearest cleaner whose shift covers the window, who has time left (job minutes + walking time) and the right equipment (large lots need a snow blower, owned or rented), then orders each route by nearest neighbor. Nothing is saved until the controller applies it.
- **Money.** Prices come from the rate card on the server; the client never sends a price. Homeowners pay for the most expensive window they accept and get the difference back if a cheaper window is assigned. A cleaner's balance is the sum of an append-only ledger. Payments go through a `PaymentProvider` interface with a mock implementation.
- **Data integrity in PostgreSQL.** Exclusion constraints (`btree_gist`) stop overlapping shifts per cleaner and overlapping *approved* rentals per tool; CHECK constraints guard ranges and ratings. The DAL turns violations into friendly messages.

## Cloud storage

`STORAGE_DRIVER=local` (default) stores files under `.storage/` and serves them through HMAC-signed, expiring URLs, using the same presigned-URL flow as Spaces, so nothing else changes when you switch.

For **DigitalOcean Spaces**:

1. Create a Space (e.g. region `tor1`) and an access key.
2. In `.env`: `STORAGE_DRIVER=s3`, `S3_ENDPOINT=https://tor1.digitaloceanspaces.com`, `S3_REGION=us-east-1`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`.
3. `APP_ORIGIN=http://localhost:3000 npm run storage:configure` (use your deployed URL too; comma-separate several). This sets CORS for browser uploads and a rule that expires unprocessed uploads under `raw/` after a day.

The bucket stays private. The database stores object keys only (`JobPhoto.displayKey`, `thumbKey`, `Job.comparisonKey`); pages get short-lived signed URLs after an authorization check.

## Deployment notes (optional for the course)

- Run as **one long-lived Node.js process** (`npm run build && npm start`): for example, a DigitalOcean Droplet or App Platform service plus a managed PostgreSQL database and a Space. Serverless hosts cap connection time, which cuts off the SSE stream.
- Set `BETTER_AUTH_URL` to the public URL, a strong `BETTER_AUTH_SECRET`, `STORAGE_DRIVER=s3`, `NEXT_PUBLIC_DEMO_LOGINS=false`, and run `npm run db:deploy` on release.
- Schedule `POST /api/cron/auto-confirm` (header `Authorization: Bearer $CRON_SECRET`) hourly. The controller overview also runs the same check when it loads.
- Better Auth rate-limits sign-in and sign-up per IP in production (3 per 10 seconds), so behind a proxy make sure the client IP is forwarded.

## Notes and known limitations

- **Payments are simulated** (mock provider and simulated payouts). Stripe test mode can implement `PaymentProvider`; real payouts would need Stripe Connect identity checks.
- **Single server process.** The event bus is in memory. Running several instances would need PostgreSQL `LISTEN/NOTIFY` or Redis behind the same `publish`/`subscribe` functions.
- **Routing is a heuristic.** Nearest-neighbor ordering on straight-line distance, not road routing or optimal vehicle routing.
- **Geocoding.** Nominatim's usage policy allows one request per second and asks for caching, which the app does. Set `GEOCODER=mock` to work offline; if a lookup fails, the property is placed approximately and flagged.
- **Drag-and-drop** uses the HTML5 API (desktop browsers); every job also has an *Assign to…* menu for keyboard and touch users.
- **Prisma 7 warning.** With `@prisma/adapter-pg`, Prisma's engine may run relation queries concurrently inside interactive transactions, which logs a `pg` deprecation warning. It's harmless on `pg` 8 (pinned in `package.json`).
- **Changing the schema.** Edit `prisma/schema.prisma`, run `npm run db:migrate -- --name <change>`, and commit the new migration folder. The exclusion and CHECK constraints live in a hand-written migration because Prisma's schema language can't express them; Prisma leaves them alone.
